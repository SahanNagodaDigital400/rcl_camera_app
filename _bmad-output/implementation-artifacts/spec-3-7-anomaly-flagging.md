## Intent

**Problem:** FR-22 (epics.md Story 3.7) asks that an unusual login or scanning pattern be flagged for Administrator review, "distinct from and in addition to" Story 3.6's hard scan throttle. Today nothing tracks a per-user baseline for either signal, and `deferred-work.md` DW-142 already reserves the Audit Log screen's "Flagged" filter (EXPERIENCE.md:38/:76, DESIGN.md `flagged-activity-row`) for exactly this story — the filter and row treatment exist in the UX spec but render nothing because no action produces a flag.

**Approach:** Two new `AuditAction` members (`LOGIN_ANOMALY_FLAGGED`, `SCAN_VOLUME_ANOMALY_FLAGGED`) are the flag itself — one ordinary, append-only `audit_log` row per detected deviation, written through the existing `audit.record()` (AD-4's only writer, unchanged). No new column, no `UPDATE` of any kind: `test_nothing_mutates_the_audit_table` forbids retrofitting a "flagged" bit onto an existing row, and DW-135 already anticipated the answer — "FR-22's anomaly work filters `action`." A new `apps/api/api/anomaly.py` module owns one new table, `anomaly_baseline` (one row per `(user_id, signal)`, `signal` ∈ `{'login','scan'}`), mutated by a single atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` (AD-8, `scan_throttle.py`'s exact shape) that rolls a fixed window's count into a running per-user average and reports whether the *current* window's count already exceeds that average by the configured deviation multiplier. `auth.py`'s `_authenticate` and `scan.py`'s `submit_scan` each call it — independently of Story 3.6's throttle and of each other — and, on a positive result, write the matching flag action. `GET /admin/audit` gains one boolean query parameter, `flagged`, selecting a second pair of fixed `SELECT` statements scoped to the two flag actions; `AuditLogScreen` gets the Flagged filter EXPERIENCE.md already describes.

## Boundaries & Constraints

**Always:**
- `anomaly_baseline` has exactly one row per `(user_id, signal)`, `PRIMARY KEY (user_id, signal)`, `user_id uuid REFERENCES users (id) ON DELETE CASCADE` — `scan_rate_limit`'s own precedent, never keyed on anything else.
- One atomic statement per check (AD-8): `INSERT ... ON CONFLICT (user_id, signal) DO UPDATE ... RETURNING window_count, baseline_average`. Never a `SELECT` followed by a decision followed by an `UPDATE`.
- `apps/api/api/anomaly.py` is the only module that writes `anomaly_baseline` — a new `test_source_guards.py` guard (`ANOMALY_HOME`, `test_only_one_module_writes_the_anomaly_baseline_table`) in `test_only_one_module_writes_the_scan_rate_limit_table`'s exact shape, plus `ANOMALY_HOME` added to `test_the_scan_reaches_the_files_it_claims_to`'s tuple.
- `anomaly.check_and_flag(conn, user_id, signal) -> bool` never writes to `audit_log` and never imports `AuditAction` or names `audit_log` — it only reports a boolean. The caller (`auth.py`, `scan.py`) decides whether to call `audit.record(...)`, exactly as `scan_throttle.check_and_record` returning a boolean that `scan.py` alone turns into a refusal.
- `TILEMATCH_ANOMALY_BASELINE_WINDOW_SECONDS` (default `86400.0`, one day) and `TILEMATCH_ANOMALY_DEVIATION_MULTIPLIER` (default `3.0`) are read once at import into module constants, `scan_throttle.py`'s exact env-var/fallback/overflow-guard shape (itself copied from `shared_vision/quality.py::_read_threshold`) — a documented, uncalibrated PRD OQ-13 placeholder, not a measured number. Both are shared across the two signals; epics.md's AC names one baseline window and one deviation, not four.
- A flag never blocks the action that produced it. Epics.md's own wording — "distinct from **and in addition to** Story 3.6's hard throttle" — and EXPERIENCE.md's Epic 3 state table (no "flagged" user-facing state exists anywhere in it) both say the same thing: a flagged login still issues a session, a flagged scan submission still returns its candidates. The flag is a side effect recorded for later review, never a refusal.
- Both checks run on **every** attempt, independent of the other and of the attempt's own outcome — epic-3-context.md: "a burst can trip one without the other." In `submit_scan`, `anomaly.check_and_flag(conn, user.id, "scan")` runs unconditionally alongside `scan_throttle.check_and_record`, before either can decide the response, so a throttled burst is still counted toward the volume baseline and a flagged-but-unthrottled burst still proceeds.
- Login only counts a **successful** sign-in toward the `"login"` baseline — inside `_authenticate`'s existing `conn.transaction()`, beside the existing `audit.record(..., LOGIN_SUCCEEDED, ...)` call (auth.py:783-791). A failed attempt or a lockout is already FR-4's mechanism (`throttle.py`); folding it into this baseline would conflate two different signals the way `throttle.py`'s own "Not here" section already argues against for FR-22/FR-23.
- `GET /admin/audit` gains exactly one new optional query parameter, `flagged: bool = False` (FastAPI-parsed), selecting between two existing statement pairs — never a dynamically assembled `WHERE`. The filtered pair adds `AND action = ANY(%s)` (parameterized array, the two flag actions) to `_SELECT_LATEST_ENTRIES`/`_SELECT_ENTRIES_BEFORE`'s existing text, keeping the same `ORDER BY created_at DESC, id DESC` / keyset-cursor shape untouched.
- `FLAGGED_AUDIT_ACTIONS` (the two-member set) lives once in `shared_schema/audit.py`, mirrored in `ts/audit.ts` — the single source both `audit.py`'s filtered `SELECT` and `AuditLogScreen.tsx`'s row-styling decision read from, `PAGE_SIZE`/`AuditAction`'s own twin precedent.
- New migration(s) under `infra/migrations/`, dated after `20260922T2000` (today, `20260923T*`), `IF NOT EXISTS` throughout, explicit `GRANT`, `.up.sql`/`.down.sql` pairs, added to `infra/tests/test_runner_unit.py`'s plan list and exercised in `infra/tests/test_migrate.py`.
- The audit-table docstring's stale "thirteen values" count (it is already sixteen before this story) is corrected to eighteen while this story is editing that same enum to add two more — a one-line fix riding along with a change already touching that line, not a separate cleanup task.

**Block If:** None identified — the detection mechanism, the two action names, the table shape, the read-side filter, and the UX (a filter toggle + an existing token-driven row treatment) are all fully specified from precedent (Story 3.6) and existing UX spec (EXPERIENCE.md:38/:76, DESIGN.md `flagged-activity-row`); nothing here needs an external account, domain, or credential.

**Never:**
- Never add an `UPDATE`, `DELETE` or `TRUNCATE` against `audit_log`, from any file — `test_nothing_mutates_the_audit_table` holds even inside `audit.py` itself. A flag is a new row, never a retrofit onto an old one.
- Never add a column to `audit_log`, and never touch `20260921T1000_create_audit_log.up.sql` (an applied migration, AGENTS.md:34). The flag is entirely representable by which two `AuditAction` values exist.
- Never let a flag refuse, delay, or otherwise change the response of the login or scan request that triggered it. No new refusal/error code is introduced by this story; `error-code-parity.test.ts` gains no new row for flagging.
- Never fold `anomaly_baseline` into `scan_rate_limit` or `login_attempts`, and never let `anomaly.py` write either of those tables — three separate AD-8 counters for three separate concerns, `scan_throttle.py`'s own "Not here" precedent.
- Never derive the baseline by querying historical `audit_log` rows at request time. AD-8 requires anomaly-baseline *state* to be rows mutated by one atomic increment-and-check, not a live aggregate query — and only `audit.py` may query `audit_log` regardless.
- Never let the window/multiplier numbers reach `apps/web` as a count, a percentage, or any rendered number — the flag is a visual indicator only (DESIGN.md `flagged-activity-row`), `SCAN_RATE_LIMITED`'s own precedent for a threshold that never leaves the server.
- Never add a "resolve"/"dismiss" workflow to a flagged entry. EXPERIENCE.md:76 is explicit: reviewing a flag is not itself an action with a workflow; an Administrator investigates and acts elsewhere (e.g. deactivating a user).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| No baseline yet | First-ever `check_and_flag` call for a `(user_id, signal)` | Row created, `window_count=1`, `baseline_average=NULL`; returns `False` (nothing to compare against) | No error |
| Baseline seeded, under deviation | A later window's count stays ≤ `baseline_average × TILEMATCH_ANOMALY_DEVIATION_MULTIPLIER` | Returns `False`; no flag entry written | No error |
| Baseline seeded, deviation crossed | A window's count exceeds `baseline_average × multiplier` | Returns `True`; caller writes one `LOGIN_ANOMALY_FLAGGED`/`SCAN_VOLUME_ANOMALY_FLAGGED` entry; the triggering login/scan still succeeds normally | No error (200/session issued) |
| Window elapsed | `window_started_at` older than `TILEMATCH_ANOMALY_BASELINE_WINDOW_SECONDS` | Statement rolls the just-elapsed window's count into `baseline_average` (average of old average and that count, or the count itself if this is the first rollover) and resets `window_count` to 1 for the new window | No error |
| Two signals, one user | User logs in and also submits scans in the same window | Two independent rows (`signal='login'`, `signal='scan'`); one tripping never affects the other | No error |
| Two users, same signal | User A bursts, User B does not | Only User A's row crosses its own baseline; User B is unaffected | No error |
| Env var unset or unparsable | `TILEMATCH_ANOMALY_BASELINE_WINDOW_SECONDS`/`_MULTIPLIER` missing or not a number | Falls back to the documented default; a warning is logged for a present-but-bad value | No error (fails open to the default) |
| `GET /admin/audit?flagged=true` | Administrator, some flag rows exist | `200`, only `LOGIN_ANOMALY_FLAGGED`/`SCAN_VOLUME_ANOMALY_FLAGGED` rows, same newest-first keyset paging as the unfiltered read | No error |
| `GET /admin/audit?flagged=true`, no flags yet | Administrator, no flag rows exist | `200`, `[]` — the screen shows its existing empty state, not a new one | No error |
| `GET /admin/audit` (default) | Administrator, flag rows exist among ordinary ones | Flag rows appear inline in the normal chronological order, each still rendered with the `flagged-activity-row` accent indicator | No error |

**Acceptance Criteria:**
- Given a user's login or scan-submission volume in the current baseline window exceeds their own historical average by more than the configured deviation, when that submission is processed, then a flag is raised for Administrator review (a new `audit_log` entry), distinct from and in addition to any Story 3.6 throttle outcome, and the triggering login or scan still completes normally.
- Given the baseline window and the deviation multiplier are each named, configurable values, when a test lowers the window (via backdating) or the multiplier, then the flag fires observably at the lowered bound with no code change.
- Given two different users, or the same user's login and scan activity, when one crosses its own baseline, then the other baseline(s) are unaffected — each `(user_id, signal)` pair is independent.
- Given an Administrator opens the Audit Log and selects the Flagged filter, when the request is made, then only `LOGIN_ANOMALY_FLAGGED`/`SCAN_VOLUME_ANOMALY_FLAGGED` entries are returned, newest-first, with the same paging guarantees as the unfiltered log; given the filter is off, then flagged entries still appear inline with their accent indicator.
- Given the change is complete, when `make lint` and `make test` are run, then both exit 0, and `test_source_guards.py`'s existing guards (audit immutability, one-writer-per-table) pass unchanged in every file this story does not itself add a guard for.

## Design Notes

**Why "pattern deviates from baseline" is operationalized as a volume/count deviation, not literal time-of-day or IP-set tracking.** Epics.md's own AC is the authoritative, testable contract: "a login or scanning pattern falls outside a user's established baseline by more than the configured deviation ... a test must be able to seed a baseline, drive a deviation past it, and observe the flag." The story's preamble names "unusual login times, locations, or scanning volume" as the motivating *examples*, but AD-8 fixes the *mechanism*: anomaly-baseline state must be Postgres rows mutated by a single atomic increment-and-check, the same shape `login_attempts`/`scan_rate_limit` already use — not a live aggregate over historical rows (which would also require a second file reading `audit_log`, forbidden by AD-4's one-writer/one-reader guard). A rolling per-user count-vs-average deviation satisfies the AC's literal contract exactly, is directly testable by seeding-then-bursting, and needs no new external dependency (no geo-IP lookup, no timezone data neither `users` nor `sessions` currently carries).

**Why one shared table with a `signal` column, not two near-identical tables.** `login_attempts` and `scan_rate_limit` are one table each because they gate two different *resources* with two different shapes (an email-keyed pre-auth counter vs a user-keyed post-auth counter). Here both signals are the same shape end to end — same columns, same statement, same config — so a `signal` discriminator column avoids duplicating one table and one nearly-identical module twice for what is genuinely one mechanism applied to two call sites, while `PRIMARY KEY (user_id, signal)` still keeps every AD-8 property (one atomic statement per check, no cross-signal interference) intact.

**Resolving `epic-3-context.md`'s "a throttled/flagged request must be rejected" phrasing.** That compiled context document is secondary to epics.md's own AC ("distinct from **and in addition to**") and to EXPERIENCE.md's Epic 3 state table, which lists every user-facing state Epic 3 can reach and has no "flagged" entry among them. Both primary sources agree a flag never blocks; the compiled phrase is read here as describing Story 3.6's throttle only, with "flagged" swept in imprecisely during compilation.

**Why re-checking (and potentially re-flagging) on every submission within an already-over-threshold window, rather than flagging once per window.** `scan_rate_limiting`'s own precedent for "a throttled caller keeps retrying" is that every subsequent attempt is independently evaluated and independently acted on; a single audit entry per crossing would hide exactly the "how much worse is this burst getting" signal an Administrator reviewing a flag needs, and EXPERIENCE.md:76 already frames a flag as informational rather than a workflow state that needs deduplicating.
